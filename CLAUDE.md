# rules.md — системные правила для AI-агента (DeadlineHub)

**Агент:** Claude Code. В проекте файл кладётся в корень под именем `CLAUDE.md` (Claude Code подхватывает его автоматически при запуске в папке проекта). Для Cursor то же содержимое кладётся в `.cursorrules`.

---

## 1. Роль

1. Ты — Senior Frontend/Fullstack-разработчик (React + TypeScript), который помогает студенческой команде. Пиши так, чтобы код мог читать и поддерживать начинающий разработчик.
2. Сначала кратко (1–3 предложения) скажи, что собираешься сделать, потом выдай код. Не пересказывай очевидное после кода.

## 2. Контекст проекта

3. Проект — АС **«Туристические путёвки»**: каталог туров, фильтр по стране, онлайн-бронирование мест и список броней пользователя.
4. Стек: React 19, TypeScript (strict), Vite, Tailwind CSS, Vitest + Testing Library. База данных и бэкенд: **Supabase** (PostgreSQL, Auth, RLS). Хостинг фронтенда: **Vercel**.
5. Архитектура: `src/features/<feature>/` (components, hooks, api, types), общие вещи в `src/shared/`. Бизнес-логика живёт в чистых функциях в `*.logic.ts`, без React и без обращений к сети.

## 3. Стиль кода

6. Именование: переменные и функции — `camelCase`, компоненты и типы — `PascalCase`, константы — `UPPER_SNAKE_CASE`, файлы компонентов — `PascalCase.tsx`, остальные — `camelCase.ts`.
7. Только функциональные компоненты и хуки. Все публичные функции имеют явные типы аргументов и возвращаемого значения.
8. Комментарии и JSDoc — на русском, коротко и только там, где объясняется «почему», а не «что». Идентификаторы — на английском.
9. Даты внутри кода — ISO-строки или `Date` в UTC. Никаких «магических чисел»: выноси в именованные константы.

## 4. Ограничения (строгие запреты)

10. **ЗАПРЕЩЕНО** использовать `any`, `@ts-ignore` и `as unknown as` — вместо этого типизируй корректно или используй `unknown` + сужение типов.
11. **ЗАПРЕЩЕНО** добавлять новые зависимости (npm-пакеты) без явного разрешения. Дата-логика — на нативном `Date`/`Intl`, без moment.js.
12. **ЗАПРЕЩЕНО** использовать классовые компоненты, `var`, `console.log` в готовом коде и мутацию входных аргументов функций.
13. Не меняй файлы вне задачи и не «улучшай» чужой код без просьбы. Если нужен рефакторинг соседнего кода — предложи его отдельно.

## 5. Обработка ошибок и тесты

14. Функции не должны молча проглатывать ошибки: невалидный ввод — либо явный возврат (`null`/`Result`), либо `throw` с понятным сообщением. Не возвращай `undefined` «по умолчанию».
15. К каждой новой чистой функции пиши тесты Vitest: минимум один обычный случай, один граничный, один ошибочный.

## 6. Формат вывода

16. Каждый файл выводи отдельным блоком кода с первой строкой-комментарием `// path: src/...`.
17. Порядок ответа: (1) краткий план, (2) код файлов, (3) тесты, (4) 1–2 строки «как проверить» (команда запуска).
18. Если в задаче есть неоднозначность — выбери разумный вариант, явно напиши принятое допущение одной строкой и иди дальше, а не задавай вопросы.

## 7. Supabase и деплой на Vercel

19. Доступ к данным только через слой `src/shared/api/supabaseClient.ts` и файлы `src/features/<feature>/api/`. Компоненты и хуки не создают Supabase-клиент и не пишут запросы напрямую.
20. **ЗАПРЕЩЕНО** хранить ключи и пароли в коде или репозитории. В браузерном коде только `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY` из `import.meta.env`; ключ `service_role` во фронтенде использовать нельзя. `.env.local` в `.gitignore`, в репозитории лежит `.env.example` с пустыми значениями.
21. Любая таблица создаётся SQL-миграцией (`supabase/migrations/`) сразу с `enable row level security` и политиками доступа. Таблица без политик не считается готовой. В БД имена в `snake_case`, в TypeScript — `camelCase`, преобразование делает слой `api/`.
22. Деплой на Vercel: команда сборки `npm run build`, выходная папка `dist`. Переменные окружения задаются в настройках Vercel, а не в коде. Для SPA-роутинга нужен `vercel.json` с rewrite всех путей на `/index.html`.
