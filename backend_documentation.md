## 1. Архитектура (Шаги 1–2)

```
Браузер (React, Netlify)
   │  supabase-js (publishable/anon key + JWT пользователя)
   ▼
Supabase
 ├─ Auth (GoTrue): регистрация, вход, выдаёт JWT
 ├─ REST API (PostgREST): /rest/v1/tours, /rest/v1/bookings
 └─ PostgreSQL: таблицы tours, bookings, политики RLS, триггер подсчёта мест
```

**Почему Supabase, а не self-hosted:** проект учебный, нужны готовые Auth и REST API без своего сервера. Не нужны VPS и Docker; RLS даёт защиту на уровне БД. Минус: зависимость от сервиса и его бесплатных лимитов (в процессе работы упёрлись в лимит писем, раздел 8).

**Слои во фронтенде:**

```
Компонент → useTours (хук) → ToursApi (интерфейс)
                               ├─ supabaseToursApi (боевая)
                               └─ mockToursApi (разработка, тесты)
```

Компоненты не знают про Supabase. Клиент создаётся один раз в `shared/api/supabaseClient.ts`; если переменные окружения не заданы, приложение работает на mock без входа.

## 2. База данных (Шаги 1, 3, 5)

### Таблица `public.tours`

| Поле | Тип | Ограничения |
|---|---|---|
| `id` | uuid | PK, `gen_random_uuid()` |
| `title` | text | not null, длина после `btrim` 3–120 |
| `country` | text | not null, длина после `btrim` 2–60 |

| `seats` | integer | not null, 1–500 (всего мест) |
| `seats_booked` | integer | not null, по умолчанию 0; `tours_seats_booked_range`: от 0 до `seats` |
| `author_id` | uuid | not null, по умолчанию `auth.uid()`, FK на `auth.users` (каскад) |
| `created_at`, `updated_at` | timestamptz | `now()`; `updated_at` обновляет триггер |

### Таблица `public.bookings`

| Поле | Тип | Ограничения |
|---|---|---|
| `id` | uuid | PK |
| `tour_id` | uuid | not null, FK на `tours` (при удалении тура брони удаляются каскадом) |
| `user_id` | uuid | not null, по умолчанию `auth.uid()`, FK на `auth.users` |
| `guests` | integer | not null, 1–10 |
| `created_at` | timestamptz | `now()` |

### Подсчёт занятых мест и защита от перебронирования

Пользователь не может менять чужой тур, но его бронь должна уменьшать число мест. Поэтому места пересчитывает триггер `bookings_apply_seats` (функция `apply_booking_to_seats`, `security definer`, права на её вызов отозваны у всех ролей):

- `INSERT` брони: `seats_booked = seats_booked + guests`;
- `DELETE` брони: `seats_booked = seats_booked - guests`.

`UPDATE` блокирует строку тура, поэтому два одновременных запроса выполняются по очереди. Если мест не хватает, срабатывает ограничение `tours_seats_booked_range`, и вся вставка брони откатывается. Код ошибки Postgres `23514`; фронтенд распознаёт его по имени ограничения и показывает «Недостаточно свободных мест».

### Права на уровне колонок

Клиент не может сам задать занятые места, автора или служебные поля:

| Роль | `tours` | `bookings` |
|---|---|---|
| `anon` | всё отозвано | всё отозвано |
| `authenticated` | `SELECT`, `DELETE`; `INSERT` и `UPDATE` только колонок `title, country, start_date, nights, price, seats` | `SELECT`, `DELETE`; `INSERT` только `tour_id, guests` |

### Политики Row Level Security

| Таблица | Операция | Кто может | Политика |
|---|---|---|---|
| `tours` | SELECT | любой вошедший | `using (true)` |
| `tours` | INSERT | вошедший, от своего имени | `with check (author_id = (select auth.uid()))` |
| `tours` | UPDATE, DELETE | только автор тура | `using` и `with check` по `author_id` |
| `bookings` | SELECT | только владелец брони | `using (user_id = (select auth.uid()))` |
| `bookings` | INSERT | вошедший, от своего имени | `with check (user_id = (select auth.uid()))` |
| `bookings` | DELETE | только владелец брони | `using (user_id = (select auth.uid()))` |
| обе | любая | аноним | права отозваны |

`(select auth.uid())` вместо прямого вызова функции: так Postgres считает значение один раз на запрос, а не для каждой строки.

**Ограничение модели:** отдельной роли «менеджер» нет. Добавлять тур может любой вошедший пользователь, менять и удалять только свои туры. Для учебного проекта это упрощение, для реального нужна роль в JWT или таблица ролей.

### Важная особенность RLS

Если пользователь удаляет **чужой** тур или **чужую** бронь, PostgREST не возвращает ошибку: строка для него «невидима», затронуто 0 строк, ответ успешный. Фронтенд это учитывает: в `supabaseToursApi.ts` удаление запрашивает `.select('id')`, и пустой результат превращается в ошибку `forbidden`.

## 4. API (Шаг 4)

Использован автоматический REST API Supabase (PostgREST), собственный сервер не нужен. Базовый адрес: `https://<project>.supabase.co`. Во всех запросах два заголовка: `apikey: <публичный ключ>` и `Authorization: Bearer <access_token пользователя>`.

### Аутентификация

| Операция | Запрос |
|---|---|
| Регистрация | `POST /auth/v1/signup` · тело `{"email": "...", "password": "..."}` |
| Вход | `POST /auth/v1/token?grant_type=password` · то же тело · в ответе `access_token` |

### Эндпоинты

| Операция | Запрос | Ответ |
|---|---|---|
| Каталог | `GET /rest/v1/tours?select=id,title,country,start_date,nights,price,seats,seats_booked&order=start_date.asc` | 200, массив |
| Создание тура | `POST /rest/v1/tours` · `Prefer: return=representation` | 201, созданная строка |
| Удаление тура | `DELETE /rest/v1/tours?id=eq.<uuid>` · `Prefer: return=representation` | 200, массив с удалённой строкой (пустой, если тур чужой) |
| Мои брони | `GET /rest/v1/bookings?select=id,tour_id,guests,created_at&order=created_at.desc` | 200, только свои |
| Бронирование | `POST /rest/v1/bookings` · тело `{"tour_id": "<uuid>", "guests": 2}` | 201; **400 с кодом `23514`**, если мест не хватает |
| Отмена брони | `DELETE /rest/v1/bookings?id=eq.<uuid>` · `Prefer: return=representation` | 200, массив с удалённой строкой (пустой, если бронь чужая) |

Примеры (переменные `URL`, `KEY`, `TOKEN` задаёт пользователь):

```bash
# создание тура (author_id и seats_booked не передаются)
curl -X POST "$URL/rest/v1/tours" \
  -H "apikey: $KEY" -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" -H "Prefer: return=representation" \
  -d '{"title":"Тбилиси и Кахетия","country":"Грузия","start_date":"2026-11-08","nights":5,"price":38700,"seats":25}'

# бронирование
curl -X POST "$URL/rest/v1/bookings" \
  -H "apikey: $KEY" -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" -H "Prefer: return=representation" \
  -d '{"tour_id":"<uuid>","guests":2}'
```

### Проверка прав через интерфейс (демонстрация RLS)

Под пользователем A создать тур на 3 места и забронировать 2. Под пользователем B: тур A виден с «Осталось 1 из 3 мест», «Удалить» даёт «Недостаточно прав: это действие доступно только автору записи», брони A в «Мои брони» не видны. Студент прошёл этот сценарий на живом сайте.

## 7. Обработка ошибок и логирование (Шаг 7)

| Ситуация | HTTP | Тип в приложении | Что видит пользователь |
|---|---|---|---|
| Нет интернета, сервер недоступен | 0 / сбой fetch | `network` | «Нет соединения с сервером…» + кнопка «Повторить» |
| Нет входа или токен истёк | 401 | `unauthorized` | «Сессия истекла или вы не вошли. Войдите снова.» |
| Нет прав (RLS, чужая запись) | 403 или 0 строк | `forbidden` | «Недостаточно прав: это действие доступно только автору записи.» |
| Запись не найдена | 404 | `not-found` | «Запись не найдена…» |
| Не хватило мест | 400 + `23514` | `sold-out` | «Недостаточно свободных мест: их успели занять. Список обновлён, выберите меньше гостей.» |
| Данные не прошли проверки | 400 / 409 / 422 | `validation` | «Сервер отклонил данные. Проверьте поля формы.» |
| Ошибка сервера | 5xx | `server` | «Ошибка на сервере. Попробуйте ещё раз через минуту.» |

**Известная неточность:** лимит запросов (HTTP 429) приложение пока показывает как «Ошибка на сервере». В процессе работы это скрыло настоящую причину (раздел 8).

Ошибки формы проверяются до отправки (сообщения под полями).

**Логирование:** каждая ошибка API пишется в консоль браузера структурированной JSON-строкой модулем `shared/api/logger.ts` (уровни `info`, `warning`, `error`; в записи контекст, статус, код и текст ошибки). Серверные логи доступны в Supabase Dashboard → Logs (API, Postgres, Auth), этим и воспользовались при отладке регистрации.

**Что нашлось при отладке:**

1. **Конфликт функции в миграции.** `set_updated_at` уже существовала от миграции `deadlines`; обычный `create function` упал бы при применении. Обнаружено при чтении миграции до запуска, исправлено на `create or replace`.
2. **Регистрация: «Ошибка на сервере».** В логах Auth (Dashboard → Logs) запрос `/signup` с HTTP 429 и действием `user_confirmation_requested`: при включённом Confirm email сработал лимит писем встроенной почты Supabase. Решение: выключить Confirm email (для демо) и удалить зависшего неподтверждённого пользователя. Сообщение в интерфейсе вводило в заблуждение (раздел 7).
3. **Белый экран на Netlify.** После первого деплоя сайт показал тестовые данные без входа: переменные окружения не были сохранены в Netlify, а `VITE_*` читаются только при сборке. После добавления переменных сайт упал с `Invalid supabaseUrl: Must be a valid HTTP or HTTPS URL` (значение введено с ошибкой); консоль браузера показала причину сразу. Исправлено значением `https://<project>.supabase.co` и повторным деплоем без кэша.
4. **Одинаковые подписи в тестах.** Поле формы «Страна» и фильтр списка имели одну подпись, тест нашёл два элемента; фильтр переименован в «Фильтр по стране». Название тура и страна «Мальдивы» совпали, поиск уточнён до заголовка.
